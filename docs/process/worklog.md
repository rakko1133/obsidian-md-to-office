## 2026-11-19 処理時間の計測（高速化の検討）

- きっかけ: ユーザーから「処理を高速化したい」。推測で手を入れる前に、段ごとの処理時間を測ることにした（Claude 推奨・ユーザー同意）
- 作ったもの: `src/core/profile.ts`（`timed` / `timedSync`。ラベルは `段/細かい段`、入れ子の時間は親にも含む包含時間）。計測を始めていないときは包んだ処理をそのまま呼ぶ。`npm run obsidian:run -- --profile` で段ごとの回数・合計・平均・最大を表にする（開発用の自動実行だけ）
- 計測（Obsidian は後ろに置いた状態。Word は `word3a`・`word3b`・`mermaid`・`style` の 47 件）

| 実行 | 全体 | 主な内訳 |
|---|---|---|
| Word・Mermaid のキャッシュなし | 41.7 s | Mermaid の PNG 化 26.5 s（26 図 × 約 1.0 s）、画像の変換 5.1 s、他プラグインの描画 6.5 s、数式の画像 2.1 s。`.docx` の生成 0.6 s・書き込み 0.5 s |
| Word・キャッシュあり | 14.6 s | 画像の変換 5.1 s、他プラグインの描画 6.5 s（うち描画の静止待ち 4.5 s・図の画像化 2.0 s）、数式の画像 2.0 s |
| Excel（`excel`・`word3a` の 24 件） | 5.4 s | 画像の変換 5.1 s（表のないノートの画像も読んでいる） |
| PDF（`word3a`・`mermaid` の 38 件） | 28.5 s | 描画の静止待ち 19.3 s（38 件 × 約 0.5 s）、`printToPDF` 7.5 s |

- 分かったこと
  - `canvas.toBlob` が 1 回ごとに約 1.0 s かかっている（`mermaid/svgToPng/toBlob` 23 回で 23.4 s、`decode` は計 1.3 ms）。SVG の画像の PNG の代替・数式の画像・他プラグインの図の画像化も同じ `toBlob` を通るので、ほぼ 1 s ずつかかる。Chromium の `toBlob` は PNG の符号化をアイドル時間に回し、アイドル時間が来なければ約 1 s 後に始める作りと考えられる（Obsidian が後ろにあると描画のフレームが出ず、アイドル時間が来ない）。仮説なので、前面での計測と `toDataURL`・`OffscreenCanvas.convertToBlob` との比較で確かめる
  - 描画の静止待ち（`waitForQuiet`）は、DOM の変化が `QUIET_MS`（500 ms）続けて止まるまで待つので、1 回あたり 500 ms が下限になる。PDF では全体の 68%
  - Excel では、表のないノート（シートにならない）の画像も読み込んで変換している
  - 構文解析（計 0.07 s）・`.docx` の生成（0.6 s）・ファイルの読み書きは小さい。バッファの再利用やアルゴリズムの改善より、待ち時間の削減が効く
- 次の候補（効果の大きい順）: (1) `toBlob` の待ちをなくす、(2) 静止待ちの短縮（変化しない描画は待たない・`QUIET_MS` の見直し）、(3) Excel で表の外の画像を読まない
- 確認: `npm run lint`（エラー 0、警告 8 は以前のまま）・単体テスト 288 件（`tests/profile.test.ts` の 4 件を追加）
